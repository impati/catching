# External 프론트 지면별 정책서

## 개요

이 문서는 `external` 사용자 화면의 지면별 동작 방식을 정리한다. 코드를 직접 읽지 않아도 신청 플로우, 로그인 처리, 약관 동의, 정보 입력 흐름을 이해할 수 있도록 화면 단위로 작성했다.

현재 프론트는 `frontend/src/App.tsx`의 단일 React 앱으로 구성되어 있고, 빌드 결과는 `external/src/main/resources/static`에 배포된다.

## 전체 흐름

사용자는 아래 순서로 신청을 진행한다.

1. 목록 지면에서 신청 가능한 선착순 이벤트를 확인한다.
2. 상세 지면에서 이벤트 상태와 내 신청 상태를 확인한다.
3. 신청 버튼을 누르면 로그인 여부를 확인한다.
4. 로그인된 사용자만 약관 확인 지면으로 이동한다.
5. 약관 전체에 동의하면 약관 동의 상태를 저장한다.
6. 약관 저장에 성공하면 실제 신청 API를 호출한다.
7. 신청 성공 후 정보 입력 지면으로 이동한다.
8. 정보 입력을 완료하면 완료 지면으로 이동한다.

URL 상태는 `comeId`와 `step` query parameter로 관리한다.

| URL 상태 | 지면 |
| --- | --- |
| `?comeId={id}` | 상세 |
| `?comeId={id}&step=terms` | 약관 확인 |
| `?comeId={id}&step=information` | 정보 입력 |
| `?comeId={id}&step=complete` | 완료 |
| `?comeId={id}&step=edit` | 정보 수정 |

## 공통 인증 정책

로그인 토큰은 `localStorage`의 `catching.auth.tokens` 키에 저장한다.

API 호출 중 `401`과 `EXPIRED_TOKEN` 에러 코드가 함께 내려오면 refresh token으로 access token을 갱신한 뒤 원래 요청을 재시도한다. 갱신에 실패하면 저장된 토큰과 회원 정보를 제거하고 로그인 상태를 해제한다.

| 상황 | 동작 |
| --- | --- |
| 비로그인 사용자가 신청 버튼 클릭 | 로그인 페이지로 이동 |
| 로그인 콜백 query에 `code`, `clientId` 존재 | 토큰 교환 후 query 제거 |
| access token 만료 | refresh token으로 갱신 후 요청 재시도 |
| refresh token 갱신 실패 | 로그아웃 처리 |

## 1. 목록 지면

### 목적

사용자가 신청 가능한 선착순 이벤트 목록을 확인하는 첫 화면이다.

### 진입 조건

앱 최초 진입 또는 상세 화면에서 `목록`을 누르면 진입한다.

### 호출 API

| 시점 | API | 목적 |
| --- | --- | --- |
| 화면 진입 | `GET /v1/comes` | 선착순 이벤트 목록 조회 |

### 표시 정보

각 이벤트 카드는 다음 정보를 표시한다.

| 항목 | 설명 |
| --- | --- |
| 상태 | `ACTIVE`는 `신청 가능`으로 표시 |
| 이벤트명 | 선착순 이벤트 이름 |
| 주최자 | 이벤트 주최자 |
| 시작 시간 | 이벤트 시작 일시 |
| 잔여 인원 | `capacity - appliedEventNumber` |
| 신청 인원 | `appliedEventNumber / capacity` |

### 사용자 동작

| 동작 | 결과 |
| --- | --- |
| 이벤트 카드 클릭 | 상세 지면으로 이동 |
| 새로고침 클릭 | 목록 API 재호출 |
| 로그인 클릭 | 로그인 인증 URL로 이동 |
| 회원가입 클릭 | 회원가입 인증 URL로 이동 |
| 로그아웃 클릭 | 저장된 토큰 제거 |

## 2. 상세 지면

### 목적

선택한 이벤트의 상세 정보와 내 신청 상태를 보여준다.

### 진입 조건

목록에서 이벤트 카드를 선택하면 `?comeId={id}` 상태로 진입한다.

### 호출 API

| 시점 | API | 목적 |
| --- | --- | --- |
| 화면 진입 | `GET /v1/comes/{comeId}/active` | 이벤트 상세 조회 |
| 로그인 상태에서 화면 진입 | `GET /v1/comes/{comeId}/apply-for` | 내 신청 여부 확인 |
| 이미 신청한 경우 | `GET /v1/comes/{comeId}/information` | 정보 입력 완료 여부 확인 |

### 표시 정보

| 항목 | 설명 |
| --- | --- |
| 이벤트 상태 | 신청 가능, 마감 등 |
| 이벤트명 | 선택한 이벤트 이름 |
| 주최자와 ID | 이벤트 식별 정보 |
| 잔여 인원 | 현재 신청 가능 인원 |
| 신청 인원 | 총 정원 대비 신청 인원 |
| 참여 방식 | 예: `IMMEDIATELY` |
| 대기 정책 | 예: `WAITLIST` |
| 중복 신청 가능 여부 | `duplicable` 값 |
| 자격 | eligibility 문구 |
| 일정 | 노출, 시작, 종료 일시 |

### 신청 버튼 정책

상세 지면의 신청 버튼은 실제 신청 API를 바로 호출하지 않는다. 로그인 여부를 확인한 뒤 약관 확인 지면으로 이동한다.

| 상태 | 버튼 또는 안내 |
| --- | --- |
| 비로그인 | `로그인 후 신청` 버튼 표시, 클릭 시 로그인 이동 |
| 로그인 + 미신청 + 신청 가능 | `신청하기` 버튼 표시, 클릭 시 약관 확인 지면 이동 |
| 로그인 + 신청 여부 확인 중 | `신청 여부 확인 중...` 표시 |
| 이미 신청 + 정보 입력 미완료 | `정보 입력하기` 버튼 표시 |
| 이미 신청 + 정보 입력 완료 | `정보 입력 완료` 표시 |
| 신청 불가 | 신청 불가 안내 표시 |

## 3. 약관 확인 지면

### 목적

실제 신청 전에 신청 약관을 노출하고 사용자의 동의를 저장한다.

### 진입 조건

상세 지면에서 로그인 사용자가 `신청하기`를 누르면 `?comeId={id}&step=terms` 상태로 진입한다.

### 호출 API

| 시점 | API | 목적 |
| --- | --- | --- |
| 화면 진입 | `GET /v1/terms-groups/APPLY_FOR` | 신청 약관 목록 조회 |
| 화면 진입 | `GET /v1/terms-groups/APPLY_FOR/agreement` | 기존 동의 상태 조회 |
| 제출 | `POST /v1/terms-groups/APPLY_FOR/agreement` | 약관 동의 저장 |
| 약관 저장 성공 후 | `POST /v1/comes/{comeId}/apply-for` | 실제 신청 |

### 화면 동작

약관 목록과 기존 동의 상태를 함께 가져와서 각 약관별 checkbox 상태를 만든다.

| 조건 | 동작 |
| --- | --- |
| 약관 로딩 중 | `약관을 불러오는 중입니다.` 표시 |
| 약관 조회 실패 | 에러 문구 표시 |
| 약관 없음 | `신청하기` 버튼만 표시 |
| 약관 있음 + 일부 미동의 | `동의하고 신청하기` 버튼 비활성화 |
| 약관 있음 + 전체 동의 | `동의하고 신청하기` 버튼 활성화 |

### 제출 정책

사용자가 전체 약관에 동의해야 신청을 진행할 수 있다.

제출 payload는 현재 약관 목록 전체를 기준으로 만든다.

```json
{
  "agreements": [
    {
      "termsId": "약관 ID",
      "agree": true
    }
  ]
}
```

약관 저장에 성공하면 바로 실제 신청 API를 호출한다. 신청 성공 후에는 정보 입력 지면으로 이동한다.

### 예외 처리

| 상황 | 동작 |
| --- | --- |
| access token 만료 | 토큰 갱신 후 약관 조회 또는 저장 재시도 |
| 약관 저장 실패 | 약관 지면에 실패 메시지 표시 |
| 신청 요청 후 상태 확인 실패 | 상세 하단에 신청 확인 실패 메시지 표시 |

## 4. 정보 입력 지면

### 목적

신청 완료 후 이벤트가 요구하는 추가 정보를 입력한다.

### 진입 조건

신청 API 성공 후 `?comeId={id}&step=information` 상태로 진입한다. 이미 신청한 사용자가 상세 지면에서 `정보 입력하기`를 눌러도 진입한다.

### 호출 API

| 시점 | API | 목적 |
| --- | --- | --- |
| 화면 진입 | `GET /v1/comes/{comeId}/fields` | 입력 필드 조회 |
| 신규 입력 전 | `GET /v1/comes/{comeId}/information` | 이미 입력했는지 확인 |
| 제출 | `POST /v1/comes/{comeId}/information` | 추가 정보 저장 |

### 필드 렌더링 정책

| fieldType | UI |
| --- | --- |
| `SINGLE_DOMAIN` | select |
| `MULTIPLE_DOMAIN` | checkbox 그룹 |
| `MOBILE` | 전화번호 입력 |
| 그 외 | 일반 text 입력 |

### 검증 정책

프론트는 `required=true`인 필드가 비어 있으면 제출하지 않고 `{필드명} 항목을 입력해주세요.` 메시지를 보여준다.

서버에서 이미 정보가 입력된 상태를 `409`로 응답하면 완료 지면으로 이동한다.

## 5. 정보 수정 지면

### 목적

이미 입력한 추가 정보를 수정한다.

### 진입 조건

완료 지면에서 `정보 수정` 버튼을 누르면 `?comeId={id}&step=edit` 상태로 진입한다.

### 호출 API

| 시점 | API | 목적 |
| --- | --- | --- |
| 화면 진입 | `GET /v1/comes/{comeId}/fields` | 입력 필드 조회 |
| 화면 진입 | `GET /v1/comes/{comeId}/information` | 기존 입력값 조회 |
| 제출 | `PUT /v1/comes/{comeId}/information` | 정보 수정 |

### 동작 정책

기존 입력값을 필드별로 채운 뒤 사용자가 수정할 수 있게 한다. 제출 성공 시 완료 지면으로 이동한다.

## 6. 완료 지면

### 목적

신청과 정보 입력이 완료되었음을 사용자에게 알려준다.

### 진입 조건

정보 입력 또는 수정이 성공하면 `?comeId={id}&step=complete` 상태로 진입한다.

### 사용자 동작

| 동작 | 결과 |
| --- | --- |
| 홈으로 | 목록 지면으로 이동 |
| 정보 수정 | 정보 수정 지면으로 이동 |
| 상세 보기 | 상세 지면으로 이동 |

## 주요 상태값

### applyStatus

| 값 | 의미 |
| --- | --- |
| `idle` | 신청 상태 확인 전 |
| `checking` | 신청 상태 확인 중 |
| `applied` | 이미 신청함 |
| `not_applied` | 아직 신청하지 않음 |
| `unknown` | 신청 상태 확인 실패 |

### informationStatus

| 값 | 의미 |
| --- | --- |
| `idle` | 정보 입력 상태 확인 전 |
| `checking` | 정보 입력 상태 확인 중 |
| `completed` | 정보 입력 완료 |
| `not_completed` | 정보 입력 미완료 |
| `unknown` | 정보 입력 상태 확인 실패 |

## 선택한 화면 설계 이유

신청 버튼에서 바로 신청 API를 호출하지 않고 약관 확인 지면을 별도로 둔 이유는 신청 전에 사용자가 약관을 명시적으로 확인하고 동의해야 하기 때문이다.

대안으로 상세 지면 안에 약관을 접어서 넣는 방식도 가능하지만, 상세 지면은 이미 이벤트 정보와 신청 상태를 보여주는 역할이 크다. 약관 동의는 실제 신청 직전의 별도 의사결정이므로 `step=terms` 지면으로 분리하는 편이 흐름과 책임이 더 명확하다.

## 테스트와 검증

프론트 변경 후 아래 명령으로 검증했다.

```bash
npm run build
npm run lint
./gradlew :external:compileKotlin
```

빌드 시 Vite 산출물이 `external/src/main/resources/static`에 갱신된다.

## 남은 확인 사항

- 약관 중 필수/선택 구분이 필요하면 API 응답에 필수 여부가 추가되어야 한다. 현재 프론트는 신청 약관 전체 동의를 요구한다.
- 약관 내용이 길어질 경우 별도 펼침/접힘 UI가 필요할 수 있다.
- 운영 DB에는 `member_agreement` 테이블이 필요하다. `data-rds/src/main/resources/ddl.sql`에 DDL이 추가되어 있다.
